## 4. 高可靠技术实现
### 4.1 高可靠ws连接
1 设计目标
- 快速恢复：网络中断或服务重启后，3秒内自动恢复连接
- 消息可靠：确保消息不丢失、不重复
- 用户无感：断线重连过程不影响用户操作
  2 实现方案
  2.1 连接保活
- 心跳检测：前端每30秒发送心跳，后端10秒未响应则判定连接失败
- 定时重连：前端采用指数退避重连（1s/2s/4s/8s...上限30s）
  2.2 消息保障
- 唯一消息ID：每条消息携带唯一ID
- 消息缓存：后端缓存消息，断线重连后补发

### 4.2 合理的信号灯显示
1 设计目标
2 实现方案
2.1 整体显示策略
- 可预置信号灯规格，三维场景中根据规格渲染对应的三维模型（待定）
  2.2 信号显示及切换策略
- 使用固定策略+微调策略+紧急策略的模式，策略可提前绑定，但只有当一个显示周期结束时才可切换策略
- 固定策略：规定从某个时间点开始，每种颜色的亮起时间，并且时间为固定的
- 微调策略：规定在每个变化周期内，哪个信号灯的哪个颜色多亮多长时间、哪个颜色少亮多长时间
- 紧急策略：默认不绑定此策略，只有在紧急情况时才绑定此策略，并且此策略的优先级最高（即此策略启用时，固定策略与微调策略自动失效）

### 4.3 合理的数据修复及关联结构
1 背景说明
- 本项目中的路网数据来自OSM，OSM的数据来自所有用户自行上传，导致部分路网数据可能存在缺失、错误
- 保存路网数据的表的结构来自osm2pgsql（一个用于将OSM数据导入到pgsql的工具）自动生成，为确保以后能正常增量新增数据，相关表的表结构不做二次修改
  2 解决方案
  2.1 路网数据相关
- 新建一张路网纠错表，用于手动纠错
- 在执行所有跟路网相关的操作时，如果纠错表有数据，则优先使用纠错表内的数据
- 对于路网数据的增删改查操作，封装一个专门的类
  2.2 路口数据相关
- 路口数据缺失较多，故新建一张路口数据表，用于手动添加路网数据，同时也作为路口纠错表使用
- 新建一张中间表，来保存路网-路口的对应关系
- 路口数量是否需要记录？路口是否需要与信号灯上的灯一一对应？（待探讨）
  2.3 信号灯数据相关
- 信号灯数据手动添加，同时也新建一张中间表来保存信号灯-路口对应关系

### 4.4 导航算法
1 设计目标
- 接入第三方部门，为特种车辆提前开路
  2 实现方案
- 查询出以起点-终点的中点为圆心，起点-终点距离的2/3为半径的所有道路、路口及信号灯数据，提交给算法
- 算法计算
- 为相关信号灯调整微调策略、绑定紧急策略

## 5. 实现细节
### 5.1 信号灯显示及调度
#### 表结构
- 信号灯策略类型表 与 信号灯策略调度表 为一对多关系
- 信号灯策略调度表 与 信号灯策略参数表 为一对多关系
- 信号灯组 与 信号灯策略类型 为一对一关系
- 子信号灯 与 信号灯策略调度 为一对一关系
- 信号灯组-信号灯策略关联修改日志表
- 策略执行日志表

#### 业务逻辑
- 信号灯组 绑定 信号灯策略类型表，子信号灯 绑定 信号灯策略类型下的信号灯策略调度，随后子信号灯根据策略来显示对应的灯
- 信号灯组的信号灯策略类型修改后，需等待一个信号灯周期结束后再进行切换
