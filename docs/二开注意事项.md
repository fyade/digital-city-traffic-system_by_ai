## 二、两套权限体系说明

项目中的两套权限体系是为**不同场景**设计的，**不要合并**：

### 体系A：RBAC 权限（MainModule 系统管理模块）

- 数据库表：`sys_menu`、`sys_role`、`sys_role_permission`、`sys_user_role` 等
- 适用场景：项目内部用户（管理员、操作员）对本系统各功能模块的访问控制
- 实现位置：`PermissionGuard` 中 `ifSF !== true` 的分支
- 特点：标准 RBAC（用户→角色→权限点），支持超级管理员旁路、接口级 IP 白名单、限流

### 体系B：SF 权限（AlgorithmModule 算法接口模块）

- 数据库表：`sys_interface`、`sys_interface_group`、`sys_user_group`、`sys_user_group_permission`、`sys_user_user_group` 等
- 适用场景：控制用户调用**外部第三方算法服务**的权限
- 实现位置：`PermissionGuard` 中 `ifSF === true` 的分支（通过 `@Authorize({ ifSF: true })` 标记）
- 特点：
  - 接口分组 + 逐接口权限控制
  - 支持请求次数限制、请求时限等配额参数
  - 权限可向上继承（`ifUseUp` 字段）
  - 与 RBAC 体系独立运作，不共享权限数据

**结论**：两套体系数据表虽然有相似命名（如 `sys_interface` vs `sys_menu`），但服务于完全不同的业务场景，合并会带来不必要的复杂度。

## 三、数据库操作约定

我（Claude Code）只有**项目文件的读写权限**，没有数据库操作权限。需要修改数据库结构时：

1. **告知用户**需要执行什么 SQL 或表结构变更
2. **用户手动操作数据库**
3. **用户手动执行** `pnpm generate:prisma` 重新生成 Prisma 客户端（到 `prisma-generated/` 目录）
4. 生成完成后通知我，我再继续后续代码修改

这个流程不需要我参与数据库操作和 Prisma 生成步骤。

## 四、项目核心设计原则（来自此前分析）

1. **所有删除均为软删除**（`deleted = 'N'/'Y'`），不物理删除数据
2. **所有表统一审计字段**：`create_by`、`update_by`、`create_role`、`update_role`、`create_time`、`update_time`
3. **API 返回统一格式**：`R<T>` = `{ code, data, msg, time, timestamp }`
4. **OSM 路网表结构不可修改**：`planet_osm_*` 表的字段结构由 osm2pgsql 自动生成，必须保持原样
5. **前端双 UI 体系**：Element Plus（管理端 `/home`、`/user`） + Naive UI + Cesium（大屏端 `/dashboard`）
6. **信号灯计算为系统核心算法**：位于 `DctsCalculateService.calculateLight()`（555行），固定策略+微调策略+紧急策略三层优先级

## 五、目录结构约定

后端目录结构：
```
server/src/module/{域}/{业务名}/{模块名}/
  dto.ts
  {模块名}.controller.ts
  {模块名}.module.ts
  {模块名}.service.ts
  {模块名}.facade.service.ts    (可选，给其他模块复用)
```
或者业务简单时不分子模块：
```
server/src/module/{域}/{业务名}/
  dto.ts
  {业务名}.controller.ts
  {业务名}.module.ts
  {业务名}.service.ts
  {业务名}.facade.service.ts
```

前端目录结构（与后端一一对应）：
- `admin/src/api/module/{域}/{业务名}/{模块名}/` 或 `.../{域}/{业务名}/`
- `admin/src/dict/module/{域}/{业务名}/{模块名}/` 或 `.../{域}/{业务名}/`
- `admin/src/type/module/{域}/{业务名}/{模块名}/` 或 `.../{域}/{业务名}/`
- `admin/src/views/module/{域}/{业务名}/{模块名}/` 或 `.../{域}/{业务名}/`

**是否分模块**：业务复杂就分子模块，不复杂就一个业务目录即可。

## 六、CRUD 路由约定

每个模块固定 **9 个** 标准 CRUD 端点：

| 方法 | 路由 | 用途 |
|------|------|------|
| GET | `/` | 分页列表 |
| GET | `/all` | 全部记录 |
| GET | `/ids` | 批量按 ID 查询 |
| GET | `/:id` | 单个按 ID 查询 |
| POST | `/` | 新增一条 |
| POST | `/s` | 批量新增 |
| PUT | `/` | 更新一条 |
| PUT | `/s` | 批量更新 |
| DELETE | `/` | 删除 |

所有响应统一用 `R<T>` 包裹：`{ code, data, msg, time, timestamp }`，成功用 `R.ok(data)`。

## 七、代码生成

本项目当前写的是全单表增删改查，二开时可以写多表联查。
